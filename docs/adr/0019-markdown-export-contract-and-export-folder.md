# ADR 0019: Markdown Export Contract and Export Folder

**Status**: Proposed (Windows fork)
**Date**: 2026-10-28
**Builds on**: [ADR 0017: Record Then Transcribe on Windows](0017-record-then-transcribe-on-windows.md), [ADR 0018: Optional, Selectable Summary Model](0018-optional-selectable-summary-model.md)
**Context**: The fork does not summarize in the app by default. The Markdown file is the only interface with the tooling that reads a meeting afterwards (an LLM driven by the user's own skills), so its shape matters more than the in-app views. The export written until now was a bullet list with raw second counts (`[123.4s - 126.0s]`), no metadata, and it needed a save dialog each time.

## Decision

The Markdown export follows PRD requirement R5.

- **One file per meeting**: a YAML front matter, a blank line, then one line per transcript segment, then any summaries under `## Summary: <template>`.
- **Front matter**: `title`, `date`, `duration`, `speakers`, `status`.
  - `date` is the local wall-clock time of the meeting, `YYYY-MM-DDThh:mm:ss`, without an offset. A reader wants the time on the user's own clock.
  - `duration` is `hh:mm:ss`. It falls back to the end of the last segment when the meeting has no recorded duration.
  - `speakers` lists each distinct display name once, in order of first appearance, and is left out when no speaker is known.
  - `status` is `to-summarize` until at least one summary exists, then `summarized`.
  - Values that YAML could misread (a colon, a quote, `true`, a number) are double-quoted.
- **Lines**: `[hh:mm:ss] Speaker: text`, sorted by start time with a stable sort so simultaneous segments of the two tracks keep their stored order. Whitespace and line breaks inside a segment collapse to single spaces. A segment with no known speaker has no `Speaker:` prefix.
- **`language` and `source` are omitted.** The meeting record stores neither (Parakeet detects the language per segment and exposes no meeting-level value), and guessing them would give the downstream tool wrong metadata. They can be added once the app really knows them.
- **Export folder**: an absolute folder stored under the `export` key of `preferences.json`. Choosing one turns exporting on; clearing it turns it off. There is no separate switch.
- **Automatic**: the file is (re)written right after a save that changes its content: end of recording, import, re-transcription, diarization, speaker rename or reassignment, segment edits, and summary generation. Renaming the title or archiving does not trigger it.
- **File name**: `YYYY-MM-DD_hh-mm_<title-slug>.md` in local time. It is deterministic, so a later export overwrites the same file instead of piling up copies. The date prefix also rules out reserved Windows device names. Renaming a meeting's title later therefore leaves the old file next to a new one.
- **Safe write**: the file is written to a hidden temporary name and renamed, so a tool watching the folder never reads half a file.
- **Never fails the caller**: an export problem (full disk, unplugged drive) is logged and the recording, transcription or summary that triggered it still succeeds.

The manual **Markdown** export from the save dialog uses the same renderer, so both paths produce the same file. Text and JSON exports are unchanged.

## Rationale

### Why change the Markdown format instead of adding a fourth one?

The fork has a single consumer for the Markdown file, and it needs the new shape. Two Markdown shapes would be a trap. The cost is that this renderer and its tests diverge from upstream; they live in one function and one test file.

### Why not accept any folder only after a confirmation, or confine it like the save dialog?

The save-dialog export is confined to the home directory because its destination travels from the webview. The export folder is picked in Settings by the user and the file name is generated by the app, never supplied by the webview. The user's notes folder can legitimately live on another drive, so only an absolute, usable directory is required.

### Why export on every change and not only at the end?

Diarization and speaker renames change the file the reader sees, and a summary changes `status`. Re-exporting is cheap (a few kilobytes), and the stable file name makes it idempotent.

## Consequences

- A new `time` feature (`local-offset`) is enabled for the local clock; when the platform cannot tell, UTC is used.
- The export folder setting has its own small facade on the UI side rather than growing `MeetingsFacade`.
- Existing integration tests of the old Markdown shape were rewritten for the new one.

## Open Risks

- No `language` or `source` field yet.
- A title change leaves the previous file behind.
- Mixed-language meetings carry no per-line language marker.
